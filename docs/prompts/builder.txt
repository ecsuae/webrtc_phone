# =========================================================
# SECTION: DEPLOYMENT-FIRST ARCHITECTURE RULES
# Prevent "works on my machine" architecture.
# =========================================================

All projects must be deployment-first.

Mandatory rules:

- Every required service must run inside Docker
- No localhost-only dependencies
- No host-installed services
- No host-installed postgres/mysql/redis/node/python services
- No manual OS dependency assumptions
- No machine-specific paths

Project must boot on fresh server using only:

git clone <repo>
cp .env.example .env
docker compose up -d

Everything must work through containers.

Required services must be containerized when applicable:

- backend
- frontend
- postgres/mysql
- redis
- celery worker
- celery beat
- nginx/reverse proxy
- scraper workers
- browser automation
- AI workers
- vector databases
- ollama containers
- cron jobs
- monitoring services

Never require:

- local python virtualenv
- local npm install
- local postgres
- local redis
- local ffmpeg
- local chrome
- local playwright

Use containers instead.

All infrastructure must include:

- restart policies
- health checks
- persistent named volumes
- proper docker networking
- environment variable support

Secrets must come from:

.env

Never hardcode:

- API keys
- passwords
- tokens
- secrets
- credentials
- internal IPs

Every new project must include:

- docker-compose.yml
- Dockerfile
- .env.example
- docs/deployment.md

If multiple services exist:

docker/
    backend/
    worker/
    nginx/
    scraper/

For scraping:

Prefer:
- Apify API
- Playwright containers
- Scrapy containers

For AI:

Prefer API-first architecture:
- OpenRouter
- OpenAI
- Anthropic
- Apify APIs

Only deploy local LLMs when explicitly required.

All generated repos must be:

- GitHub ready
- CI/CD ready
- VPS ready
- reproducible
- migration safe

- do not re-architect unless docs explicitly require it

If another AI’s previous change looks wrong:
- stop before editing

- propose one safe correction step

- identify active task
- identify known-good baseline
- identify last verified state
- identify exact next safe step

Never say “based on previous chat”.
Use only repository docs and files.
